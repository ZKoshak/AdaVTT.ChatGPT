Я бы ещё с самого начала ввёл пакет конфигурации проекта.

Например:

```ada
package VTT_Config is

   Ada_83_Mode   : constant Boolean := False;
   Ada_95_Mode   : constant Boolean := True;

   Compiler_GNAT     : constant Boolean := True;
   Compiler_GW_GNAT  : constant Boolean := False;

   Platform_DOS      : constant Boolean := False;
   Platform_Linux    : constant Boolean := True;

end VTT_Config;
```

Для современных компиляторов это может генерироваться автоматически через `.gpr`, а для старых компиляторов — поддерживаться вручную.

---

Ещё один совет для совместимости со старыми компиляторами: не использовать иерархические пакеты в публичном API.

То есть вместо:

```ada
package VTT.Core.Memory is
```

лучше:

```ada
package VTT_Core_Memory is
```

Причина проста: Ada'83 не знает child packages, а некоторые древние Ada'95-компиляторы реализовывали их с ограничениями.

Если целью действительно являются такие системы, как Janus Ada, Artek Ada и особенно Meridian Ada, то стиль именования времён Ada'83 может оказаться более практичным.

Я бы предложил в качестве первого шага определить **минимальный поддерживаемый поднабор языка** для ядра проекта.

Например:

### Уровень Core-95

Разрешено:

- packages;

- child packages (по желанию);

- tagged types;

- generics;

- controlled types;

- Streams.

Запрещено:

- protected types;

- tasking;

- аспекты Ada 2012+;

- интерфейсы Ada 2005+ в ядре.

Тогда код будет собираться даже очень старыми реализациями Ada'95, а современные возможности можно будет подключать через `runtime/ada2005+` и выше.

Это позволит сохранить единое ядро и не превратить проект в набор расходящихся веток под каждый стандарт языка.
