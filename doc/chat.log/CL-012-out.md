Для AdaVTT я бы сразу строил CI не как для обычного проекта на GNAT, а как для **долгоживущего кросс-платформенного проекта**, где современные GitHub Actions используются для автоматизации, но архитектура не зависит от них.

На текущем этапе достаточно 2–3 workflow, но их стоит заложить так, чтобы потом не пришлось всё переделывать.

# 1. Базовая проверка сборки

`.github/workflows/build.yml`

Цель:

- проверка синтаксиса;

- проверка зависимостей;

- сборка через `gprbuild`.

Пока достаточно Linux.

Например:

```yaml
name: Build

on:
  push:
  pull_request:

jobs:
  build-gnat:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - name: Install GNAT
        run: |
          sudo apt-get update
          sudo apt-get install -y gnat gprbuild

      - name: Build
        run: |
          gprbuild -P adavtt.gpr
```

На данном этапе этого уже достаточно.

# 2. Проверка стиля

Я бы ввёл её сразу.

Например:

```yaml
name: Style
```

Пока даже без специальных инструментов.

Проверять:

- отсутствие табуляции;

- окончания строк;

- отсутствие CRLF в репозитории.

Пример:

```bash
grep -r $'\t' src/
```

и падение сборки при обнаружении табов.

# 3. Проверка дерева проекта

Очень полезно для крупных проектов.

Например:

```yaml

```

Проверять наличие:

Это кажется мелочью, но со временем помогает.

# Отдельный workflow для исторических компиляторов

Сразу закладывать не нужно.

Но я бы оставил каталог:

```text
.github/workflows/legacy/
```

или

```text
ci/
```

для будущих скриптов.

Потому что:

- GW-GNAT

- Meridian

- Artek

через GitHub Actions нормально не установить.

# Что бы я сделал прямо сейчас

Минимальный набор:

```text

└── workflows/
    ├── build.yml
    └── style.yml
```

и корневой:

```text
.gitignore
```

```gitignore

*.o
*.exe

Thumbs.db
```

---

Для AdaVTT с заявленной поддержкой старых компиляторов я бы ещё с самого начала добавил каталог:

```text
ci/
```

в корень проекта:

```text
AdaVTT/
│
├── ci/
│   ├── build_gnat.sh
│   ├── build_gwgnat.bat
│   ├── build_janus.bat
│   └── build_meridian.bat
```

Даже если большинство файлов пока пустые.

Тогда GitHub Actions будет лишь запускать эти скрипты, а логика сборки останется частью проекта и сможет использоваться вне GitHub — на локальных машинах, self-hosted runner'ах, DOSBox и исторических системах. Для проекта с такими требованиями к переносимости это обычно гораздо более устойчивое решение, чем завязывать процесс сборки непосредственно на YAML-файлы Actions.
