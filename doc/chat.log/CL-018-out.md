Отлично. Сейчас как раз тот этап, когда такие вещи нужно **зафиксировать архитектурно**, но **не реализовывать**. Самая частая ошибка больших проектов — начать писать код, а потом через год обнаружить, что базовые предположения были неверны.

Я бы оформил это как набор архитектурных принципов AdaVTT.

---

# Архитектурная заметка №1: Mapping System

Пока не реализовывать.

Но зафиксировать:

> Исходное дерево проекта является каноническим и не зависит от ограничений конкретного компилятора, ОС или файловой системы.

Следствие:

```text
src/
```

— единственный источник истины.

Все адаптации:

- DOS 8.3;

- особенности GW-GNAT;

- особенности Janus Ada;

- особенности Meridian Ada;

выполняются через отдельный слой трансформации.

Например:

```text
tools/
compat/
ci/
```

но никогда не через ручное изменение исходников.

---

# Архитектурная заметка №2: Единый ABI

Это намного важнее, чем может показаться сейчас.

Я бы зафиксировал:

> Все объекты, события и сетевые сообщения используют единое бинарное представление.

Неважно, работают ли они:

- внутри процесса;

- между потоками;

- между сервером и клиентом;

- между разными версиями AdaVTT.

---

Например, в будущем должно быть возможно:

```text
Event
↓
Memory
↓
File
↓
Network
↓
Replay Log
```

без преобразования структуры.

То есть событие должно иметь один ABI.

---

# Архитектурная заметка №3: Сетевой код не является специальным случаем

Очень важно.

Многие VTT делают ошибку:

```text
GUI
↓
Game Logic
↓
Network Layer
```

---

Лучше:

```text
GUI
↓
Commands
↓
Event Bus
↓
Game State
```

и уже потом:

```text
Network
```

передаёт те же команды.

---

Тогда:

```text
локальная игра
```

и

```text
игра через интернет
```

используют один код.

---

# Архитектурная заметка №4: Роли пользователей

Очень хорошо, что ты поднял этот вопрос сейчас.

Я бы уже сегодня зафиксировал, что роль — это свойство сессии, а не приложения.

---

То есть не так:

```text
Server.exe
Player.exe
GM.exe
```

---

А так:

```text
AdaVTT
↓
Role
```

где роль может быть:

```text
Dedicated_Server
Game_Master
Assistant_Game_Master
Player
Observer
```

---

Даже если позже появятся урезанные сборки.

---

# Архитектурная заметка №5: Варианты сборки

Это уже касается будущего разделения модулей.

Сейчас я бы предполагал три целевых профиля.

---

## Full

```text
adavtt
```

Содержит всё.

---

## Server

```text
adavttd
```

или

```text
adavtt_server
```

Без:

- UI;

- рендера;

- аудио.

---

## Client

```text
adavtt_client
```

Без:

- выделенного серверного режима;

- серверных административных инструментов.

---

Но важно:

> Все три варианта используют одно и то же ядро.

---

# Архитектурная заметка №6: Представление мира

Очень важный пункт.

Нужно зафиксировать:

> Игровой мир не зависит от способа визуализации.

То есть:

```text
Map
Token
Light
Wall
Zone
```

существуют сами по себе.

---

А потом уже:

```text
2D Top Down Renderer
3D Isometric Renderer
3D First Person Renderer
```

отображают один и тот же мир.

---

Нельзя делать:

```text
2D Map
3D Map
```

как разные сущности.

---

# Архитектурная заметка №7: Сервер не знает о графике

Я бы зафиксировал это сейчас.

Сервер работает только с:

```text
State
Events
Assets
Rules
Permissions
```

---

Никаких:

```text
Sprite
Texture
Mesh
Camera
```

на сервере существовать не должно.

---

# Что это означает для AVTT_Memory

Очень многое.

Когда начнём проектировать память, нужно учитывать, что в будущем в памяти будут жить:

```text
Objects
Events
Commands
Assets
Map Data
Network Packets
```

---

Поэтому я бы уже сейчас сформулировал главный принцип для модуля памяти:

> AVTT_Memory не знает, что хранится в памяти.

Он должен управлять только:

```text
Allocate
Free
Pool
Arena
Stack
Static Block
```

---

То есть память должна быть полностью универсальной.

---

# Что я бы записал в архитектурный журнал проекта

На данный момент уже можно считать зафиксированными следующие решения:

1. Каноническое дерево исходников не зависит от компилятора.

2. Для legacy-компиляторов будет создан Mapping System.

3. Все события, объекты и сетевые сообщения будут использовать единый ABI.

4. Сетевой режим не является особым случаем игровой логики.

5. Роль пользователя определяется сессией, а не приложением.

6. Full, Server и Client версии используют единое ядро.

7. Игровой мир независим от способа визуализации.

8. Сервер не зависит от графической подсистемы.

9. AVTT_Memory является универсальным менеджером памяти и не зависит от типов хранимых объектов.

После такой фиксации уже вполне безопасно переходить к проектированию `AVTT_Memory`, потому что основные архитектурные решения, влияющие на память, уже обозначены.
